# 教室容量（座位數）

寫於 2026-09-07。

## 目標

把 `Croom.jsp?format=-3` 頁面上的「容量(座位數)」收進資料集，讓使用端算得出
「這門課的修課人數 vs 教室座位數」。目前 `enrolled` 是修課人數、**不是名額上限**
（`models.py:83` 有證據），所以那個比率的分母現在拿不到。

## 已驗證的事實

設計建立在三個實驗上，都是實抓驗證的，不是推論。**共三個請求。**

| # | 實驗 | 結果 | 推論 |
|---|---|---|---|
| 1 | `code=48&year=115&sem=1` | 三教307(e)／容量 **50**／日間 37 節 82.22% | 容量確實在這頁上 |
| 2 | `code=48&year=110&sem=1` | 同名稱／容量 **50**／日間 27 節 60.00% | 跨 5 年容量相同，使用率不同 |
| 3 | `code=48&year=199&sem=1` | 同名稱／容量 **50**／使用率與週課表**全空** | **容量來自教室主檔，與學期無關** |

實驗 3 是關鍵。`year` / `sem` 只影響使用率與週課表；容量不受影響，連不存在的學年度
都照樣回傳。

**因此：學校沒有保留歷史容量。** 一間教室改建之後，所有學期的頁面都會一起顯示
新容量 —— 「110-1 當時是幾個座位」這個資訊在來源端就不存在，我們無法補救。

另從本地既有資料（51 個學期的 `classrooms.json`，零網路請求）確認：

- 全部學期出現過 **445** 個教室代碼，**沒有任何代碼對到不同名稱**（0 衝突）
- 115-1 的 234 個代碼全部在其他學期出現過
- 另有 211 個代碼只出現在舊學期

代碼是穩定的識別碼，可以直接當主鍵。

## 資料形狀

### 新增根目錄 `capacity.json`

```json
{
  "schema_version": 3,
  "generated_at": "2026-09-07T02:00:00Z",
  "classroom_count": 445,
  "classrooms": {
    "48": {
      "name": "三教307(e)",
      "full_name": "第三教學大樓307室",
      "capacity": 50,
      "checked_at": "2026-10-01T02:14:33Z"
    }
  }
}
```

- **`capacity`** 是最近一次觀測到的值；讀不出來時是 `null`，**不是 0** ——
  「沒讀到」和「零個座位」是兩回事，跟 `runs.json` 的 `detail: false` 同一個原則。
- **`checked_at`** 每次重抓都更新，即使值沒變。用來分辨「值一直是 50」和
  「很久沒去看了」。

**不留改建歷史。** 值變了就直接覆蓋 —— 使用者要的是「現在幾個座位」，不是
沿革。這也讓每一筆固定四個欄位，不會隨時間長大。

約 445 筆 × 約 55 bytes ≈ **25 KB**。

### 既有的 `{semester}/classrooms.json` 每筆多一個欄位

```json
{"id": "48", "name": "三教307(e)", "capacity": 50, "course_count": 18, ...}
```

值取自 `capacity.json` 的現值，**寫檔時不發任何請求**。狀態檔沒有該代碼時填 `null`。

實作上 `_write_classrooms()` 目前只收得到 `semester_dir`，需要多傳根目錄才讀得到
狀態檔 —— 這是這個功能唯一要動到既有寫檔路徑的地方。

> **已知的語意限制（必須寫進 README）**：因為學校不保留歷史容量，所有學期的
> `capacity` 都是**最近一次觀測值**，不是那個學期當時的容量。教室改建後，
> 舊學期的數字也會跟著變成新值。這是來源端的限制，無法補救。

## 抓取策略

新增 CLI 旗標 `--with-capacity`，搭配 `--max-capacity N` 可分批。

挑選規則兩條：

1. **代碼不在 `capacity.json` 裡** → 抓（首次建表、日後有新教室時）
2. **`--capacity-refresh-after HOURS`（預設 480 小時＝20 天）已過** → 重抓

沒有「永久凍結」機制 —— 容量會因改建而變，凍結的話改建後的新值就永遠抓不到。
但也不會每次 crawl 都重抓：門檻讓常態成本維持在零。

> 門檻**刻意小於一個月**。排程是每月 1 號，但二月只有 28 天，加上 Actions 的
> cron 實測常延遲 2~4 小時 —— 門檻若設 30 天，二月那輪會因為「還沒過 30 天」
> 而整批跳過。20 天留足了餘裕。

用哪個學期的 URL 去抓？用**我們自己資料裡該教室最後出現過的學期**。那些頁面
確定存在，而且由實驗 3 可知這個選擇不影響容量值。

一輪全量重抓 = 445 個請求 × 1.2 秒 ≈ **9 分鐘**。

## 執行位置

新增獨立的 `capacity.yml`，每月 1 號 UTC 02:00 觸發（`cron: '0 2 1 * *'`），
外加 `workflow_dispatch`。

- 與 `crawl` 共用 `concurrency: crawl` —— 不與其他抓取同時對學校發請求
- 排在同一天 06:00 的整包重建**之前**，讓重建帶著最新的容量發布
- 那個時段沒有 4 小時排程的班次（00:00 與 04:00 之間），不會自己撞自己
- **不掛在 crawl.yml**：crawl 每 4 小時一班且要維持在 9 分鐘內，不該加不可預期
  的抓取階段
- **不掛在 backfill.yml**：那支是「補歷史、可分批」的語意，容量重抓是週期性的
  維護，兩者混在一起會讓 `remaining` 守門的判斷變複雜

## 錯誤處理

- 單一教室抓失敗 → 記進 `errors.json`（`stage: "classroom"`，帶 `classroom_id`
  與 `url`），**不中斷整批**。它不會進狀態檔，所以下次執行自動重試。
- 頁面抓得到但解析不出容量 → 寫入 `capacity: null` 並照樣記 `checked_at`，
  同時在 `errors.json` 留一筆。避免因為版面改了而無聲地一直重抓。
- 整批失敗 → 沿用既有的 workflow 重試機制（等 30 分鐘、最多 3 次）。

## 測試

全部離線，沿用 `tests/conftest.py` 的 `no_real_network` 安全網。

1. **解析器**（純函式，吃 HTML 字串）：新增 fixture `croom_page_real.html`
   （即實驗 1 抓到的那頁）。測正常頁、容量欄位缺漏、頁面結構壞掉三種。
2. **狀態檔**：值沒變時只更新 `checked_at`；值變了就覆蓋 `capacity`。
   兩種情況都不新增欄位 —— 每一筆永遠是固定四個鍵。
3. **挑選規則**：不在狀態檔的會被選中；在狀態檔且未過期的會被跳過；
   `--max-capacity` 會截斷。
4. **寫檔**：`{semester}/classrooms.json` 的每筆都補上 `capacity`；狀態檔沒有的
   代碼填 `null` 而不是 0。
5. **workflow**：`capacity.yml` 的 YAML 可解析、有 schedule 與 workflow_dispatch。

## 刻意不做

- **使用率統計**（日間／夜間／週末的節數與使用率）。它們隨課表變動、不能凍結，
  而且與現有的 `schedule.json` 資訊重疊。使用者已明確表示只要容量。
- **週課表**（頁面下半部）。每格是 `(課號) [43人]課名`，這些我們已經從課表頁
  拿到了，重複抓沒有價值。
- **回頭補歷史容量**。來源端就沒有，做不到（見「已驗證的事實」）。

## 相容性

依 README §`schema_version` 與相容性承諾：「**新增欄位、新增端點不會升版**」。

- `{semester}/classrooms.json` 多一個 `capacity` 欄位 → 新增欄位
- 根目錄多一個 `capacity.json` → 新增端點

兩者都不升版，`schema_version` 維持 **3**。README 的端點表與 `meta.json` 的
`endpoints` 清單要同步新增一列。
